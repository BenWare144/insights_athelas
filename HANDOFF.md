## What this project is

A browser add-on that automates chart-note busywork in **Athelas Insights** (a physical-therapy EHR at insights.athelas.com). It ships as a **Tampermonkey userscript** (source of truth) and a generated **Chrome MV3 extension** (same code, MAIN world). Its headline value: the AI scribe files interventions under the wrong CPT code, and this tool moves each to the right code (97110/97112/97530) with the correct justification in one click — plus survey/goal helpers on initial evals, calendar shortcuts, and a settings panel to toggle features. It collects/transmits no data and runs only on Athelas.

Five requests have come out of the compliance review. **Four are built; one (the cue rule) is still blocked on decisions.**

1. ✅⚠ **Non-reimbursed billing codes → an appropriate PT CPT.** Built. `NON_REIMBURSED` in `matching/procedure-matching.js` maps **98960 → 97535**; Fix Procedures moves items off it (name rule picks the destination when it has one, "leave alone" rules overridden). Deliberately an open family — adding a code is a one-line change plus the mirror. **But on 2026-09-04 the compliance director wrote that she removed 98960 from the clinic's fee schedule and "He does not need to add that rule!"** — so the specific 98960 mapping may now be dead weight at Choice Therapy. 2. ⏸ **"Provider cues" documented → 97112.** BLOCKED on decisions — the evidence review is `matching/cues-and-simulation-review.md` (what it would catch, the 8 conflicts, and why it can't be a name rule). Headline: cue language is in the intervention **details**, not the name, so this changes the matcher's shape; it would move 6 of 254 real items and fix 2 wrong downgrades, but a bare "cue" mention also catches ordinary exercise instruction.
3. ✅ **"Simulate / replicates" → 97530.** Built in 15.25.0, per the therapist's ruling (2026-09-22): match `simulat*`/`replicat*` against the intervention **details** (`[aria-label="Intervention details"]`), and on a conflict **this rule wins over every other rule**. It is now rule 0 in `RULES`, which also means it overrides the "leave alone" excludes (TKE, Bridges, curtsey-step) — accepted with the ruling, but the one behaviour to keep an eye on when bridges are finally settled. Move-only: the detail sentence is its own justification. `reproduc` is deliberately excluded ("symptom reproduction" is the opposite of simulating a task). Zero regressions across all 254 real interventions — nothing in the corpus uses the phrasing yet, because every capture is Cheri's and this is the compliance director's own habit ("I usually verbalize with patient what the task replicates or simulates"). **Still worth getting one of her notes** to confirm the scribe echoes the phrasing rather than paraphrasing it away. Details in `matching/cues-and-simulation-review.md`.
4. ✅ **Diagnosis "S → D".** Built as the **Fix Diagnosis** button — confirmed to be the ICD-10 7th-character episode indicator. Adds the `…D` code, verifies it landed, then removes the `…S` code.

5. ✅ **Plan of Care on an eval should default to 90 days** (requested 2026-09-04; built in 15.23.0 as **Fix Plan of Care**). Problem as stated: the therapist tells the patient what they'll *start* with, the scribe writes that into the eval's plan — "1x/week for 4 weeks" — and therapists don't change it, so the POC expires early. Built as a review-first red/green button in the Plan of Care header on eval notes; lengthens `duration` to 12 weeks, lets the app re-derive end date and visit count, writes them only if it doesn't. Two caveats to carry back to the clinic:
   - **12 weeks is confirmed** (clinic, 2026-09-06). They asked for "90 days"; 90 days is 12.86 weeks, so 12 weeks (84d) is the longest whole number of weeks inside a 90-day certification and 13 (91d) would overshoot. The clinic accepted 12 weeks, so the days-vs-weeks question is CLOSED — no need to check whether the Duration-Units Select offers "Days". `window.__athelasDurationUnitOptions()` remains as a diagnostic if it ever matters again, and the target stays a per-unit map so a form already set to days/months still gets a sane value.
   - **Agreed by both directors** (confirmed to Ben 2026-09-06; the second director's "yes" came outside the email thread, which ends on the question). Cleared for company-wide rollout. It still has its own Extension Settings switch, so an individual therapist can turn it off.
   - **It is now an actual default** (15.24.0), which is what was originally asked for: the fix applies itself the first time an evaluation opens, with an Undo in the toast, and the note gets exactly one automatic attempt ever. The app has no "first load" signal to hang that on — only the four free-text sections carry a "Last updated" chip, and `plan_of_care` has none — so we keep our own record of seen note keys in localStorage. See DECISIONS.md for the guards and the honest limit ("first time on this browser", not "first time ever").

1. **The rest of the non-reimbursed list.** 98960 is handled. What else, and what's each target? Also: is 98960 → 97535 always right, or does it want to be a settings choice?
2. **Provider cues → 97112** (the "simulate" half is now settled and shipped). See the open questions at the end of `matching/cues-and-simulation-review.md` — chiefly (a) bare cue mention vs cue + purpose word, (b) what justification sentence a cue rule should append, (c) whether a cue mention overrides the parked Bridges rule, and (d) **does the cue rule also get top priority?** The simulate ruling set a precedent, but it does not automatically carry over: 97112 pays less than the 97530 rules a top-priority cue rule would outrank, so "higher-paying wins" argues it should sit *below* them instead.
3. **Confirm the reimbursement ordering.** The "higher-paying category wins" tie-break is currently assumed to be 97530 ≳ 97535 > 97112 > 97110 (typical Medicare PFS). Confirm against Choice Therapy's actual fee schedule before it becomes precedence — 97530 and 97535 are close enough that a contract could invert them.
4. **Role differentiation (exploratory, on hold).** Cheri asked the clinic this directly on 2026-08-25 — "would [98960 → 97535] work for all disciplines, or do you want just specifically for PTs?" — and **it was never answered**; the thread moved on. Can the page tell us the user's discipline? **Yes, and it is the LOGGED-IN user, not just the note's provider** (resolved in 15.23.1). The credential (`DPT`, `PT`, `OTR/L`, `CCC-SLP`, …) appears only in `[data-section="notarize"] section[aria-label="Provider(s)"]`; the row that is *you* is the one owning the **Sign** button (or the disabled "Signed" button once the note is signed) — you can only sign as yourself, while co-signers show "Awaiting Signature". Do NOT use the "Supervising Provider" label for this: on several notes Cheri is herself labelled Supervising Provider and still owns the Sign button. `athProviderInfo()` / `window.__athelasProviderInfo()` return `{providers, me, source}`; `athDiscipline()` maps the credential to PT/OT/SLP, returning null rather than guessing. Verified against all 11 distinct provider blocks in `captures/` — 11/11 correct — with the harness at `captures/_provider-detect-harness.html` (git-ignored; serve the folder over http and open it, since local files don't run scripts in a preview pane; it embeds a *snapshot* of the functions, so re-extract them from the userscript before trusting a re-run). Nothing is gated on any of it. If OT can't bill a PT activity and needs an OT-specific code, `NON_REIMBURSED` becomes a per-discipline map.
   - Not available anywhere else: the app shell, nav, and user menu carry no name or credential (only a `/my_account` link), and there is no inline JSON/`__INITIAL_STATE__` to read — the SPA fetches everything. The remaining alternatives are a same-origin API call (which would break the documented "no network" claim) or harvesting `/my_account` if the user visits it (no capture of that page yet).
5. **Company-wide vs Cheri-specific:** the matching rules are one shared set. Should these new rules apply to all Choice Therapy therapists, or stay Cheri's? If therapists want different code mappings (not just on/off), that implies per-user config beyond the current toggles.

## How to work here (the short version)

- Edit the userscript (and the canonical `matching/` or `surveys/` file first for logic). Bump the version in all four spots, regenerate `content.js`, `npm test`, `npm run build:local`, rebuild the store zip, update `CHANGELOG.md`. Commit locally; **don't push**.
- Verify DOM behavior on the live site or an `.mhtml` capture in `captures/` (PHI — never leaves the repo). When you can't verify, say so.
- Watch the recurring gotchas in `DECISIONS.md` (esp. `align-self: flex-end` for right-alignment, and MUI `mousedown` to open selects).
